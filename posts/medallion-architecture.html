Why Your Medallion Architecture Is Secretly a Monolith

May 2025 · 8 min read · Pipelines

The medallion architecture — Bronze, Silver, Gold — has become the default mental model for modern data lakehouses. It's clean, intuitive, and makes for great slide decks. But in practice, I've watched it become something engineers dread touching: a tightly coupled, slow-moving monolith wearing the costume of a layered system.

This isn't a knock on the pattern itself. The idea is sound. The problem is in how teams implement it, and specifically, in the assumptions baked into the data flow between layers.

A layered architecture is only as modular as the contracts between its layers. Without explicit contracts, layers become implicit dependencies — and implicit dependencies are just coupling with better PR.

The problem

Here's the typical setup: raw data lands in Bronze. A set of dbt models or Spark jobs transforms it into Silver — cleaned, deduplicated, typed. More transformations produce Gold — the business-ready aggregates that power dashboards and ML features.

This feels modular. Each layer has a job. But look closer at what actually ties them together: the schema of the upstream table. Silver models reference Bronze column names directly. Gold models reference Silver column names directly. Add a column in Bronze and you might need to propagate that change through ten models. Rename something in Silver and Gold breaks.

That's not a layered architecture. That's a pipeline graph where every node is coupled to the schema of every node above it.

How it happens

The coupling accumulates gradually, which is why it's easy to miss. No one decides "let's build a monolith." It happens like this:

  • A Silver model selects * from a Bronze table because it's convenient.
  • A Gold model uses five specific columns from Silver — columns that were never formally documented as a stable interface.
  • Six months later, a source system changes a column name. Bronze is updated. Silver's SELECT * silently passes through the new column name. Gold suddenly has a missing column and fails at 3am.

The root issue is that schemas are not contracts. Treating them as such is the original sin of most data pipelines. 

-- The problem: implicit coupling via SELECT *
-- Silver model
SELECT *
FROM bronze.raw_events
WHERE event_type IS NOT NULL

-- If bronze.raw_events renames a column, this silently passes
-- the new name downstream. Gold breaks. Nobody knows why.

What to do about it

The fix isn't to abandon the medallion pattern — it's to introduce explicit contracts at layer boundaries.

1. Be explicit about what you consume

Never use SELECT * across layer boundaries. Explicitly name every column you depend on. This documents the interface and makes breakage loud and immediate rather than silent and delayed. 

-- Better: explicit column selection creates a visible contract
SELECT
    event_id,
    user_id,
    event_type,
    created_at,
    session_id
FROM bronze.raw_events
WHERE event_type IS NOT NULL

2. Use schema tests as contract enforcement

In dbt, not_null and accepted_values tests are useful, but what you really want are schema tests that assert column presence. If Bronze renames user_id to customer_id, your Silver model should fail immediately in CI — not at runtime in production.

3. Version your interfaces, not your tables

When a Silver table is consumed by many Gold models, treat it like an API. Define what's stable. When you need to change something, deprecate the old column before removing it. This is boring discipline, but it's the difference between a system teams trust and one they fear.

The best data architectures I've worked in had one thing in common: engineers knew exactly what they could rely on and what was internal. That clarity comes from explicit contracts, not from hoping nobody touches the Bronze layer.

Conclusion

The medallion architecture is a good pattern. But like most good patterns, it requires discipline to preserve the properties that make it good. The moment layer boundaries become implicit — the moment you're relying on schema stability as a substitute for actual contracts — you've built a monolith.

The fix is unglamorous: explicit column selection, schema tests, and treating your layer interfaces like the APIs they actually are. None of this is revolutionary. But it's the difference between a data platform that scales and one that becomes a legacy system before it's two years old.
